## 1. 系统/方法概述

该仓库没有使用统一的异常类库或全局错误中间件，而是采用**“返回类型化结果 + 结构化事件 + 请求-回复协议”**的组合方式，在 Electron 主进程、Agent Worker 线程、渲染进程之间传递错误。

核心思路：
- 同步/阻塞路径通过 `throw new Error(...)` 抛出普通 Error，由调用方捕获后转换为持久化的错误字符串。
- 跨进程异步调用统一通过 `AgentRequestBroker` 的 `{ ok: true; data } | { ok: false; error: string }` 回复结构传递错误。
- 长生命周期任务（turn）的错误通过 `SequencedAgentEvent` 中的 `turn.failed` 事件携带 `error: string` 字段推送给 UI。
- 所有跨进程消息都经过 `isDesktopRequest` / `isAgentEvent` 等运行时校验器，非法消息直接拒绝而不进入业务逻辑。

## 2. 关键文件与职责

| 文件 | 错误处理职责 |
|---|---|
| `src/shared/domain.ts` | 定义 `ModelConnectionResult` 联合类型（`ok: true/false` + `status` 区分 `offline` / `model-mismatch` / `connected` / `concurrency-warning` / `slots-unverified`），以及 `TurnRecord.error`、`ThreadRuntimeState.error` 等持久化错误字段。 |
| `src/shared/protocol.ts` | 定义 `DesktopRequest` 联合类型、`SequencedAgentEvent`（含 `turn.failed`）、`AgentEvent`；提供 `isDesktopRequest`、`isAgentEvent` 等运行时校验函数，对非法消息直接返回 `false`，避免错误扩散。 |
| `src/shared/operationErrors.ts` | 集中定义用户可读的业务错误常量（如 `ACTIVE_THREAD_DELETE_ERROR`、`ACTIVE_GROUP_DELETE_ERROR`），供上层 `throw new Error(...)` 引用。 |
| `src/main/agentRequestBroker.ts` | 封装主进程与 Agent Worker 的请求-回复通道：`AgentReply = { type: 'agent.reply'; requestId; ok: true; data? } | { type: 'agent.reply'; requestId; ok: false; error: string }`；超时、端口断开时统一 `reject(new Error(...))`。 |
| `src/agent/worker.ts` | 工作线程入口：`handlePortMessage` 中 try/catch 将业务异常包装为 `postReply(requestId, false, undefined, safeErrorMessage(error))`；turn 执行失败时调用 `database.failTurn(turnId, now(), message)` 并发送 `turn.failed` 事件。 |
| `src/agent/database.ts` | 提供 `failTurn(turnId, completedAt, error: string)` 将错误写入 SQLite `turns.error` 列；`TurnRecord` 和 `ThreadRuntimeState` 均包含可选 `error?: string` 字段用于持久化。 |
| `src/agent/modelConnection.ts` | 模型连接探测不抛错，而是返回 `ModelConnectionResult` 联合类型：`offlineFailure`、`modelMismatchFailure`、`slotsUnverified` 分别对应不同失败状态。 |
| `src/renderer/components/SettingsView.vue` | 渲染层消费 `ModelConnectionResult` 的 `status` 字段显示诊断信息；catch 块中将 `error.message` 写入 `modelStatus` 展示给用户。 |
| `src/shared/redaction.ts` | 通过 `safeErrorText` / `safeErrorMessage` 过滤敏感信息（如 API Key），确保错误消息安全地跨进程传输。 |

## 3. 架构与约定

### 3.1 连接/能力探测：返回类型化结果而非抛错
`inspectModelConnection` 不会抛出网络异常，而是根据 `fetch` 是否成功、HTTP status 是否为 200、JSON 是否可解析、模型 ID 是否匹配、slots 数量是否一致，分别返回 `offline`、`model-mismatch`、`slots-unverified`、`concurrency-warning`、`connected` 五种状态。调用方（SettingsView）依据 `status` 决定 UI 文案。

### 3.2 长任务（turn）：事件流 + 最终失败事件
`execute` 函数包裹整个 turn 执行：
- 正常完成 → `completeTurn` 成功后发送 `turn.completed`。
- 任何异常 → 先检查 `signal.aborted`（取消），否则用 `safeErrorMessage` 清洗错误文本，写入 `database.failTurn`，再发送 `turn.failed { error }`。
- 取消路径通过 `AbortSignal` 传播，`withExplicitAbort` / `abortReason` 保证取消被识别为 `AbortError`。

### 3.3 请求-回复：统一 `ok` 标记
`AgentRequestBroker` 将每个请求分配 `requestId`，Worker 侧 `handlePortMessage` 用 try/catch 捕获业务异常后调用 `postReply(requestId, false, undefined, safeErrorMessage(error))`；主进程收到 `{ ok: false, error }` 后 `reject(new Error(reply.error))`。超时也统一 reject。

### 3.4 业务校验错误：常量 + throw
删除线程/分组前检查是否有活跃 turn，命中则 `throw new Error(ACTIVE_THREAD_DELETE_ERROR)`，错误常量集中在 `operationErrors.ts`，便于测试断言和用户提示复用。

### 3.5 输入校验：运行时类型守卫
`protocol.ts` 中的 `isDesktopRequest`、`isAgentEvent` 对所有跨进程消息做白名单式校验，未知 `type` 或字段缺失直接返回 `false`，防止脏数据进入业务层。

## 4. 约定与约束

- **跨进程错误必须序列化**：Worker 侧只允许传递字符串错误（`error: string`），禁止透传对象/堆栈，通过 `safeErrorMessage` 限制长度（500 字符）并脱敏。
- **连接探测不抛错**：`modelConnection.ts` 中所有网络异常都被捕获并映射到 `ModelConnectionResult` 的 `status`，调用方必须 switch on `status`。
- **turn 错误必须持久化**：所有非取消的失败都必须调用 `database.failTurn`，同时设置 `incomplete = 1`，以便 UI 能显示历史失败记录。
- **取消优先于错误**：`signal.aborted` 检查在多处出现（`inspectModelConnection`、`execute`、`withExplicitAbort`），取消不应被视为业务错误。
- **无全局错误中间件**：错误处理分散在各模块的 try/catch 中，没有统一的 middleware 或全局 unhandled rejection 处理器；这是当前代码库的实际状态。
- **UI 层不直接 catch 底层 Promise**：SettingsView 中 `testProfile` 使用 try/catch 仅用于将错误转为 `modelStatus` 文案，真正的连接状态仍依赖 `ModelConnectionResult.status`。

## 5. 适用性说明

本仓库属于 Electron + Vue 桌面应用，错误处理贯穿主进程、Worker 线程、渲染进程三层，采用 TypeScript 联合类型 + 运行时校验 + 结构化事件的模式，具有明确的边界和约定，因此本类别适用且证据充分。
