# P0：代码 Agent 核心闭环

## 1. 目标

P0 的目标是让 Private AI Desktop 从“模型生成代码文本”升级为“在用户授权的工作区内读取、修改并验证代码的 Agent”。

P0 完成后，客户端必须能够以受控方式执行以下完整流程：

```text
理解任务 -> 搜索代码 -> 读取上下文 -> 提出或应用补丁
-> 运行验证 -> 读取错误 -> 继续修复 -> 审查差异 -> 结束任务
```

## 2. 范围

P0 包含八个不可缺失的能力包：

1. 代码模式和任务契约。
2. 工作区选择、规范化和权限边界。
3. 统一工具协议和工具路由。
4. 文件、搜索、补丁、命令和 Git 基础工具。
5. 模型—工具—结果循环。
6. 代码任务上下文和压缩。
7. 构建、测试和最终差异验证。
8. 任务状态、取消、重试和恢复证据。

P0 不包含 LSP、浏览器自动化、MCP、并行子 Agent 和企业策略中心。

## 3. 代码模式

### 3.1 模式隔离

通用聊天和代码任务必须使用不同的行为契约：

- 聊天模式只回答，不获得工作区写权限。
- 代码只读模式可以搜索和读取，但不能修改或执行有副作用命令。
- 代码修改模式可以在授权范围内应用补丁和运行非破坏性验证。

模型配置与 Agent 模式分离。选择同一个本地模型时，用户仍可选择普通聊天或代码工作区。

### 3.2 代码系统指令最低要求

代码模式的系统指令应简洁并明确：

- 先检查项目和相关文件，再提出修改。
- 不编造文件、接口、命令结果和测试结果。
- 使用工具获得事实；工具失败时读取错误再判断。
- 优先小范围补丁，保留用户已有修改。
- 不执行超出用户目标的重构。
- 修改后运行与风险匹配的验证。
- 没有完成时不能因为单次输出结束而宣称完成。
- 最终结果必须列出修改、验证和剩余风险。

工具描述、审批边界和终止条件由独立结构提供，不重复堆入系统提示。

## 4. 工作区与权限

### 4.1 工作区实体

建议新增 `WorkspaceRecord`：

```ts
interface WorkspaceRecord {
  id: string;
  displayName: string;
  rootPath: string;
  canonicalRootPath: string;
  trustLevel: 'read-only' | 'read-write';
  networkPolicy: 'disabled' | 'allowlisted';
  createdAt: string;
  lastOpenedAt: string;
}
```

根路径必须使用系统真实路径规范化，防止 `..`、符号链接、目录联接或大小写差异绕过边界。

### 4.2 文件访问规则

- 所有目标路径必须解析为工作区根目录下的绝对路径。
- 默认排除 `.git` 内部对象、密钥文件、二进制文件、构建缓存和依赖目录。
- 读取单文件、单次搜索和目录枚举均设置大小与数量上限。
- 文件写入只允许通过补丁工具，不提供任意字节覆盖接口。
- 新文件、删除文件和重命名单独标记为更高风险操作。

### 4.3 命令访问规则

- 命令必须有固定工作目录。
- 命令参数以数组传递，不通过不受控字符串拼接跨 Shell 执行。
- 设置超时、输出字节数、子进程数量和取消信号。
- 默认禁用网络、提权、系统服务、注册表和工作区外写入。
- 依赖安装、删除、迁移、发布和外部写操作必须审批。

## 5. 工具协议

### 5.1 统一请求

```ts
interface AgentToolCall<TInput = unknown> {
  callId: string;
  turnId: string;
  toolName: string;
  input: TInput;
}
```

### 5.2 统一结果

```ts
interface AgentToolResult<TOutput = unknown> {
  callId: string;
  status: 'success' | 'error' | 'cancelled' | 'approval-required';
  output?: TOutput;
  error?: {
    code: string;
    message: string;
    retryable: boolean;
  };
  truncated?: boolean;
  durationMs: number;
}
```

工具结果必须区分业务失败、策略拒绝、用户取消、超时和输出截断。禁止只返回一段无法可靠分类的文本。

### 5.3 模型兼容策略

优先顺序：

1. 模型支持原生工具调用时使用结构化调用。
2. 不支持时，使用严格 JSON Action 协议。
3. JSON 解析失败只允许有限次格式修复重试。
4. 连续失败后进入明确的 `tool-protocol-failed` 状态，不把原始内容当作命令执行。

任何情况下都不得从普通 Markdown 代码块中自动提取并执行命令。

## 6. P0 工具清单

### 6.1 `workspace_tree`

用途：获取受限深度的目录树。

关键输入：相对路径、最大深度、最大条目数。

关键输出：路径、类型、大小、是否被忽略、是否截断。

### 6.2 `search_code`

用途：使用 `rg` 或等价能力搜索文本、文件名和正则表达式。

关键输入：查询、glob、大小写策略、最大结果数。

关键输出：文件、行号、短片段、结果是否截断。

### 6.3 `read_file`

用途：按行读取文本文件。

关键输入：路径、起止行。

关键输出：带行号文本、编码、总行数、内容哈希。

内容哈希用于补丁前置检查，防止模型基于旧版本覆盖新修改。

### 6.4 `apply_patch`

用途：创建、更新或删除工作区内文件。

关键要求：

- 只接受统一补丁或结构化文件操作。
- 应用前校验基线哈希。
- 应用后返回变更文件、行数和冲突。
- 默认先预览，再按权限策略自动应用或请求审批。
- 保存可撤销的反向补丁或 Git 检查点引用。

### 6.5 `run_command`

用途：运行构建、测试、格式化和只读诊断命令。

关键输出：退出码、stdout、stderr、耗时、超时、截断状态。

命令策略不得只按可执行文件名称判断安全性，还应结合参数、副作用类别和工作目录。

### 6.6 `git_status` 与 `git_diff`

用途：识别用户修改、限定 Agent 修改范围、进行最终审查。

P0 只开放只读 Git 操作。提交、推送、切分支和重写历史不属于 P0 自动能力。

## 7. Agent 编排循环

### 7.1 状态机

```text
created
 -> orienting
 -> gathering-context
 -> model-deciding
 -> waiting-tool
 -> applying-change
 -> verifying
 -> reviewing
 -> completed | failed | cancelled | needs-user
```

每个状态都必须持久化时间、当前步骤、已用轮数和最近错误。

### 7.2 单轮流程

1. Context Builder 生成当前工作上下文。
2. Model Adapter 请求模型生成消息或工具调用。
3. Tool Router 验证工具名称和参数。
4. Approval Policy 判断是否需要用户确认。
5. Tool Runtime 执行并返回结构化结果。
6. 结果写入任务事件和上下文。
7. Orchestrator 判断继续、重试、验证或终止。

### 7.3 终止条件

完成必须同时满足：

- 模型明确给出完成声明。
- 没有未结束的工具调用或审批。
- 所需补丁已经成功应用。
- 至少完成风险匹配的验证，或明确记录无法验证的原因。
- 最终差异没有超出授权范围。

以下情况停止为 `needs-user`：

- 需要扩大任务范围。
- 发现与用户修改冲突。
- 需要破坏性或外部操作。
- 缺少无法从工作区获得的关键选择。

以下情况停止为 `failed`：

- 工具协议连续解析失败。
- 同一错误在限定重试后无进展。
- 超过任务轮数、时间或资源上限。
- 工作区或安全策略拒绝继续。

## 8. 上下文工程

### 8.1 上下文分层

每次模型请求按以下顺序组织：

1. 稳定系统指令。
2. 当前模式、权限和可用工具。
3. 项目规则摘要。
4. 用户原始目标和最新补充要求。
5. 任务台账。
6. 当前相关代码片段。
7. 最近工具结果和验证错误。
8. 当前待决事项。

### 8.2 代码任务台账

```ts
interface CodingTaskLedger {
  objective: string;
  constraints: string[];
  completedSteps: string[];
  pendingSteps: string[];
  inspectedFiles: string[];
  changedFiles: string[];
  latestVerification?: VerificationSummary;
  unresolvedErrors: string[];
}
```

台账是压缩后的任务事实，不保存隐藏思维链。

### 8.3 75% 压缩策略

保留现有约 75% 阈值，但代码模式压缩需要专用规则：

必须保留：

- 原始任务和后续约束。
- 当前项目规则。
- 变更文件和补丁摘要。
- 最近一次验证命令、退出码和关键错误。
- 未解决问题和下一步。
- 工具审批结果。

可以压缩：

- 已过时的目录树。
- 已被新内容替代的文件片段。
- 重复成功日志。
- 较早的自然语言讨论。

禁止通过截断 data URL、补丁关键上下文或错误核心行来节省 Token。

## 9. 验证闭环

### 9.1 验证发现

按项目文件识别推荐命令，例如：

- `package.json`：类型检查、测试、构建、lint。
- `go.mod`：`gofmt`、`go test`、`go vet`。
- `pom.xml`/`build.gradle`：对应测试和构建。
- `pyproject.toml`：pytest、类型和格式检查。

发现命令只是建议，最终仍受工作区规则和审批策略约束。

### 9.2 失败反馈

失败结果应抽取：

- 命令和工作目录。
- 退出码。
- 关键错误行。
- 关联文件位置。
- 输出是否截断。

模型根据真实错误继续修复。不得只把完整大日志重复塞入上下文。

### 9.3 最终审查

任务完成前必须检查：

- `git status` 和完整变更文件清单。
- 是否包含缓存、密钥、数据库、日志或生成物。
- 是否存在调试代码和未完成标记。
- 是否修改了无关文件。
- 最终验证是否针对最新代码运行。

## 10. UI 要求

- 显示当前工作区和授权模式。
- 区分模型消息、真实工具调用和工具结果。
- 工具调用按步骤折叠，不重复堆叠相同加载提示。
- 补丁提供逐文件预览、接受、拒绝和撤销。
- 命令显示工作目录、参数、状态、耗时和退出码。
- 长任务显示当前阶段，而不是只显示“思考中”。
- 用户可随时取消；取消必须终止模型请求和关联子进程。

## 11. 安全要求

- Renderer 保持 `contextIsolation`，不得启用 Node Integration。
- IPC 输入必须通过共享协议校验。
- 路径校验在 Utility Process/Tool Runtime 执行，不能只依赖 UI。
- 日志和错误信息需要密钥脱敏。
- 工具结果不得把工作区外敏感环境变量回传模型。
- 补丁和命令审计记录必须可关联到 task、turn 和 tool call。

## 12. P0 验收摘要

P0 只有在以下场景全部通过后才可标记完成：

1. 在只读模式下解释陌生模块且不发生写入。
2. 搜索、读取并修改一个小型 TypeScript 缺陷。
3. 测试首次失败后，Agent 根据错误修复并再次通过。
4. 脏工作树中保留用户已有修改。
5. 路径穿越和工作区外写入被阻止。
6. 破坏性命令进入审批，不被自动执行。
7. 上下文达到阈值后仍保留任务、差异和验证状态。
8. 取消任务后模型流和命令进程均停止。

详细条目见 [验收矩阵](05-acceptance-matrix.md)。
