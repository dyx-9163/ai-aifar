# P1：项目智能与可恢复工作流

## 1. 目标

P1 在 P0 可执行闭环之上，提高 Agent 对具体项目的理解能力、规则一致性和长任务恢复能力。

P1 解决的问题不是“模型能不能写一段代码”，而是：

- 是否遵守这个仓库的构建、测试和安全规则。
- 是否找到真正相关的文件、符号和调用链。
- 是否理解当前 Git 状态和用户已有修改。
- 是否能在应用重启或上下文压缩后继续同一个工程任务。

## 2. 前置条件

P1 依赖以下 P0 能力已经稳定：

- 工作区安全边界。
- 结构化工具协议。
- 文件、搜索、补丁、命令和 Git 只读工具。
- Agent 循环和验证闭环。
- 代码任务台账。

如果 P0 尚未完成，不应先开放 Skill 脚本或自动 Git 操作。

## 3. `AGENTS.md` 项目规则

### 3.1 发现顺序

建议实现与 Codex 相近的分层规则：

1. 用户级全局 `AGENTS.override.md`，不存在时读取 `AGENTS.md`。
2. 从 Git 根目录走到当前工作目录。
3. 每一级优先读取 `AGENTS.override.md`，否则读取 `AGENTS.md`。
4. 根目录规则先加载，离当前目录更近的规则后加载并覆盖冲突项。

客户端必须显示本次任务实际加载了哪些规则文件，避免隐藏规则导致用户无法解释行为。

### 3.2 内容预算

- 设置规则总大小上限。
- 超限时提示用户，而不是静默截断关键规则。
- 保留来源路径和优先级。
- 对规则内容生成摘要时仍应允许模型按需读取原文。

### 3.3 规则类别

推荐支持：

- 项目结构和模块边界。
- 包管理器和构建命令。
- 编码、错误处理和测试规范。
- 禁止修改的目录。
- 外部操作和依赖安装审批。
- 发布和代码审查要求。
- 特定子目录覆盖规则。

## 4. `SKILL.md` 可复用工作流

### 4.1 Skill 结构

```text
.agents/skills/<skill-name>/
  SKILL.md
  scripts/       optional
  references/    optional
  assets/        optional
```

### 4.2 渐进加载

初始上下文只放入：

- Skill 名称。
- 简短描述。
- 适用和不适用范围。
- 文件位置。

当用户显式指定或任务与描述匹配时，Agent 再读取完整 `SKILL.md`。脚本和参考资料继续按需读取，不能启动时全部塞进上下文。

### 4.3 Skill 安全

- Skill 指令不能突破工作区权限和审批策略。
- Skill 中的脚本不会因为被发现就自动执行。
- 执行脚本仍经过命令工具、参数校验和审批。
- 外部下载、凭据、删除和发布行为始终需要独立授权。
- 客户端显示被激活的 Skill 及其来源。

## 5. 代码索引

### 5.1 分层索引策略

第一层使用低成本索引：

- 文件名、扩展名、大小和修改时间。
- Git 跟踪状态。
- 文本符号的快速搜索缓存。
- 忽略规则和语言分布。

第二层按需增加语法索引：

- Tree-sitter AST。
- 类、函数、接口、变量和 import/export。
- 符号定义与引用。

第三层可选接入语言服务器：

- Go to definition。
- Find references。
- 类型和诊断。
- Rename 预览。

### 5.2 索引一致性

- 文件变化后增量更新。
- 补丁应用后使相关缓存失效。
- 索引结果必须携带文件版本或哈希。
- 索引不可用时自动退回 `rg` 和按行读取，不阻塞基本 Agent 流程。

### 5.3 忽略策略

默认忽略：

- `node_modules`、构建输出和缓存。
- `.git` 对象。
- 大型二进制文件。
- 用户配置的敏感路径。

`.gitignore` 不是唯一安全依据。用户应能查看和覆盖“仅搜索忽略项”，但不能绕过安全禁止项。

## 6. Git 感知

### 6.1 基础能力

- 仓库根目录、当前分支和 HEAD。
- 工作树状态。
- 文件差异和未跟踪文件。
- 与指定基线的差异。
- 只读日志、单文件历史和 blame。

### 6.2 修改归属

任务开始时记录基线：

```ts
interface WorkspaceBaseline {
  head?: string;
  statusFingerprint: string;
  dirtyFiles: string[];
  capturedAt: string;
}
```

最终差异必须区分：

- 任务前已存在的用户修改。
- 本任务应用的修改。
- 任务过程中由外部程序产生的修改。

检测到同一文件外部变化时，Agent 不得直接覆盖。

### 6.3 检查点和撤销

优先使用非破坏性检查点：

- 保存正向和反向补丁。
- 在干净仓库中可记录 Git commit/树引用，但不自动提交。
- 在脏仓库中不能用重置工作树作为撤销方式。

撤销只撤销本任务确认归属的修改。

## 7. 长任务恢复

### 7.1 持久化状态

除现有 turn/message 外，建议新增：

- `coding_tasks`：目标、状态、工作区、模型和权限。
- `task_steps`：计划步骤及完成状态。
- `tool_calls`：工具输入摘要、状态、输出引用和审批。
- `workspace_changes`：文件操作和补丁引用。
- `verification_runs`：命令、退出码和结果摘要。
- `task_checkpoints`：可恢复状态快照。

大工具输出保存为受限本地 artifact，数据库只保存摘要、路径、哈希和大小。

### 7.2 重启处理

客户端重启后：

- 运行中的模型请求和进程不会假装继续存在。
- 任务标记为 `interrupted`。
- 校验工作区、文件哈希和 Git 基线是否变化。
- 显示上次已完成步骤和未解决错误。
- 用户确认后从安全检查点恢复。

禁止在应用启动时自动重新执行中断前的写操作。

## 8. 项目画像

Agent 可生成可审查的项目画像：

- 主要语言和框架。
- 构建、测试、格式化命令候选。
- 关键入口和模块。
- 本地开发和部署文档位置。
- 安全敏感区域。

项目画像是缓存，不是事实权威。每个结论需要来源文件和生成时间，并在相关文件变化后失效。

## 9. 任务规划

复杂任务可以维护显式步骤，但计划不是固定剧本：

- 每一步有目标、依赖和验证条件。
- 工具结果可能触发重新规划。
- 已完成步骤不得在没有原因时重复执行。
- 计划变化必须记录原因。
- 小任务允许不展示冗长计划，但内部仍需跟踪终止条件。

## 10. UI 要求

- 工作区侧栏显示项目规则和已激活 Skill。
- 文件引用可点击打开并定位行号。
- 差异视图区分用户原有修改与 Agent 修改。
- 任务恢复页面显示中断原因、基线变化和恢复风险。
- 索引状态不应阻塞基础聊天；降级时给出明确提示。
- 项目画像和自动发现命令允许用户修正。

## 11. P1 验收摘要

1. 根目录和子目录规则能按优先级加载，并显示来源。
2. 只匹配的 Skill 被按需加载，未匹配 Skill 不占用完整上下文。
3. 同名符号能通过定义和引用定位到正确文件。
4. 脏工作树中的用户修改可被准确区分和保护。
5. 应用重启后任务进入中断状态，不自动重复写操作。
6. 用户确认恢复后，Agent 能从检查点继续并重新验证文件基线。
7. 索引损坏或 LSP 不可用时，基础搜索仍可用。

详细条目见 [验收矩阵](05-acceptance-matrix.md)。
