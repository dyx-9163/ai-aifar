# Private AI Desktop 代码 Agent 建设路线图

## 1. 文档目的

本文档定义 Private AI Desktop 在不更换当前私有大模型的前提下，从通用对话客户端演进为代码 Agent 的总体架构、优先级、依赖关系和交付边界。

本目录中的文档共同构成代码能力建设基线：

- [P0：代码 Agent 核心闭环](01-p0-code-agent-core.md)
- [P1：项目智能与可恢复工作流](02-p1-project-intelligence.md)
- [P2：高级工程能力](03-p2-advanced-capabilities.md)
- [P3：平台治理与规模化](04-p3-platform-governance.md)
- [验收矩阵](05-acceptance-matrix.md)
- [官方参考资料](06-official-references.md)

本文档是架构说明，不代表所有能力已经实现。每个优先级必须单独形成实施计划、代码变更和验收记录。

## 2. 结论

客户端可以显著提高现有模型完成代码任务的能力，但不能完全消除基础模型在推理、代码知识、上下文容量和工具调用稳定性上的上限。

提升的关键不是继续扩大通用系统提示词，而是建立完整的工程闭环：

```text
用户任务
  -> 加载工作区与项目规则
  -> 搜索并读取相关代码
  -> 模型选择工具或提出修改
  -> 客户端执行工具并返回结构化结果
  -> 模型根据结果继续判断
  -> 应用补丁
  -> 运行构建和测试
  -> 根据失败继续修复
  -> 审查最终差异
  -> 交付可验证结果
```

`AGENTS.md` 和 `SKILL.md` 是这个体系的重要组成部分，但不是代码能力本身：

- `AGENTS.md` 负责项目约束和工作约定。
- `SKILL.md` 负责可复用的专项流程。
- 工具执行层负责真正读取、修改和验证代码。
- Agent 编排循环负责持续工作直到满足终止条件。
- 上下文管理负责在长任务中保留目标、修改、错误和证据。

## 3. 当前工程基线

当前工程已经具备以下可复用基础：

- Electron 主进程和隔离的 Preload 桥接。
- Node-enabled Utility Process Agent 运行时。
- Vue 3 渲染端和类型化事件协议。
- SQLite 会话、消息、任务、审批和模型配置持久化。
- 本地 OpenAI-compatible 模型连接与流式 SSE 解析。
- 单模型并发槽位和任务调度。
- 长输出自动续写和上下文压缩。
- 图片附件和视觉消息传递。
- 任务取消、状态指标和部分审批事件。

当前代码调用链的主要限制是：

1. `src/agent/worker.ts` 仍以单次 `runModel(...)` 为核心。
2. 系统提示是通用助手提示，没有代码模式的行为契约。
3. `tool.started`/`tool.output` 主要用于展示事件，并未形成真实工具选择与回传循环。
4. 没有工作区授权、文件读取、代码搜索、补丁应用和本地命令执行工具。
5. 没有分层加载 `AGENTS.md` 或按需加载 `SKILL.md`。
6. 聊天历史压缩已存在，但尚未形成代码任务状态、修改台账和验证证据的专用压缩策略。

## 4. 优先级定义

| 优先级 | 定义 | 未完成时的影响 | 主要交付 |
| --- | --- | --- | --- |
| P0 | 成为代码 Agent 的最低闭环 | 仍然只是生成代码文本的聊天客户端 | 工作区、工具协议、Agent 循环、补丁、命令、验证、任务状态 |
| P1 | 提升项目级理解和长任务可靠性 | 能改代码，但容易违反项目规则、找错文件或丢失进度 | AGENTS、Skills、代码索引、Git 感知、检查点、符号能力 |
| P2 | 提升复杂任务完成率和覆盖面 | 难以完成 UI 验证、跨系统调查和大型任务拆分 | 浏览器、检索、MCP、并行 Agent、专项审查 |
| P3 | 支撑产品化、企业治理和持续优化 | 能力可用但难以规模部署、审计和持续评估 | Evals、策略、审计、插件治理、性能和发布治理 |

优先级是依赖顺序，不是功能重要性的主观评分。P1 不能代替 P0，P2 也不能绕过 P0 的安全边界。

## 5. 目标架构

```text
+---------------- Renderer ----------------+
| Workspace | Chat | Diff | Terminal | QA  |
+-------------------+-----------------------+
                    | typed IPC
+---------------- Preload ------------------+
| Minimum capability bridge and validation |
+-------------------+-----------------------+
                    |
+------------ Agent Utility Process --------+
| Task Orchestrator                         |
|  + Instruction Resolver                   |
|  + Context Builder                        |
|  + Model Adapter                          |
|  + Tool Router                            |
|  + Approval Policy                        |
|  + Verifier / Reviewer                    |
|  + Checkpoint Manager                     |
+-------------------+-----------------------+
                    |
+-------------- Tool Runtime ---------------+
| Files | Search | Patch | Shell | Git | UI |
+-------------------+-----------------------+
                    |
+------------ Workspace Sandbox ------------+
| Explicit roots, policy, limits and audit  |
+-------------------------------------------+
```

### 5.1 核心边界

- Renderer 不直接访问文件系统或启动进程。
- Preload 仅暴露经过类型验证的最小能力。
- Agent Utility Process 负责任务决策、模型调用和持久化状态。
- Tool Runtime 只执行已注册工具，不执行模型任意输出。
- Workspace Sandbox 决定允许访问的根目录、命令、网络和修改范围。
- 所有可变更操作必须产生结构化审计事件。

## 6. 统一设计原则

### 6.1 证据优先

模型不得把“建议执行的命令”写成“已经执行成功”。构建、测试、差异和状态结论必须来自真实工具结果。

### 6.2 最小权限

读取、修改、命令、网络和外部系统分别授权。打开工作区不自动授权工作区之外的路径。

### 6.3 保留用户修改

Agent 必须识别脏工作树，不得覆盖与任务无关的现有修改。补丁冲突必须停止并呈现冲突位置。

### 6.4 小步修改

优先使用结构化补丁；每轮修改都应可审查、可撤销，并保持工具输出和模型判断可追踪。

### 6.5 长任务可恢复

输出 Token 到达上限不等于任务完成。长任务必须依据明确终止条件继续，同时保存目标、已完成步骤、文件修改和验证状态。

### 6.6 模型能力可降级

不能假设所有 OpenAI-compatible 模型都支持原生 Function Calling。工具协议需要同时支持：

- 原生结构化工具调用。
- 受约束的 JSON 动作协议。
- 工具调用不稳定时的解析失败重试和安全终止。

## 7. 交付依赖图

```text
P0.1 工作区与权限
  -> P0.2 工具协议与只读工具
  -> P0.3 补丁与命令工具
  -> P0.4 Agent 循环
  -> P0.5 验证与任务状态
  -> P1 项目智能
  -> P2 高级工程能力
  -> P3 平台治理
```

可以在同一优先级内并行设计，但发布必须遵守依赖顺序。例如可以同时开发搜索工具和差异 UI，但在工作区边界未完成前不得开放任意命令执行。

## 8. 推荐发布阶段

### 阶段 A：只读代码助手

- 用户选择工作区。
- Agent 可以列目录、搜索和按行读取文件。
- 能加载项目规则并解释代码。
- 不允许文件修改或命令执行。

### 阶段 B：受控代码修改

- 支持补丁预览、审批、应用和撤销。
- 支持安全的只读 Git 命令。
- 修改后展示完整差异。

### 阶段 C：验证闭环

- 支持白名单命令和项目测试。
- Agent 能根据真实错误继续修复。
- 形成完成、失败和需要人工处理的明确终止状态。

### 阶段 D：项目智能和高级能力

- 分层项目规则、Skills、符号索引、浏览器验证、MCP 和并行任务。
- 引入评测、策略和审计治理。

## 9. 不在本路线图中的内容

- 更换、微调或重新训练基础模型。
- 默认允许公网访问。
- 默认允许访问用户整个磁盘。
- 默认执行破坏性命令。
- 在没有评测证据时承诺达到某一商业模型的完全等价质量。
- 把隐藏的模型推理内容作为产品正确性的证明。

## 10. 文档和实施治理

每个实施批次必须生成：

1. 独立实施计划。
2. 明确的文件和协议变更范围。
3. 安全影响分析。
4. 自动化测试和人工验收清单。
5. 验证报告和已知限制。
6. 可恢复或回滚方式。

只有 [验收矩阵](05-acceptance-matrix.md) 中对应条目通过，能力才可从“设计”标记为“可用”。
