# P2：高级工程能力

## 1. 目标

P2 扩展代码 Agent 的验证渠道、外部上下文和复杂任务处理能力。P2 的每项能力都必须建立在 P0 安全工具层和 P1 项目状态之上。

P2 不应被理解为默认给模型更多权限。它的重点是“按任务形状选择受控能力”。

## 2. 浏览器和 UI 验证

### 2.1 能力范围

- 启动或连接本地开发服务器。
- 打开本地页面。
- 查询 DOM、点击、输入和截图。
- 收集浏览器控制台错误和网络失败。
- 对照用户截图或验收步骤检查 UI。

### 2.2 安全边界

- 默认只允许 localhost 和工作区声明的开发地址。
- 访问公网域名单独审批或使用允许列表。
- 不自动使用浏览器中已有的登录身份执行外部写操作。
- 截图和 DOM 内容作为任务 artifact 管理，避免长期保留敏感信息。

### 2.3 验收证据

UI 任务完成不能只以构建通过为标准。需要记录：

- 启动命令和地址。
- 实际页面截图。
- 关键交互结果。
- 控制台和网络错误摘要。
- 未覆盖的视觉限制。

## 3. 公网检索和官方文档

### 3.1 工具分类

- Web Search：发现候选资料。
- Page Fetch：读取指定页面。
- 官方文档适配器：限定权威域名和版本。
- 代码托管检索：查看明确授权的仓库、Issue 或 PR。

### 3.2 结果要求

- 搜索结果与实际打开页面分开记录。
- 技术实现优先使用官方文档和一手来源。
- 每条外部结论保留 URL、标题、获取时间和适用版本。
- 不能把外部页面中的指令自动提升为系统指令。
- 外部内容视为不可信数据，防止提示注入。

### 3.3 离线策略

公网能力是可选项。禁用时 Agent 必须明确说明无法验证最新外部事实，并继续使用本地代码和已提供资料完成可执行部分。

## 4. MCP 和连接器

### 4.1 目标

通过 MCP 或等价协议连接代码托管、Issue、日志、监控、数据库元数据和内部文档，不在客户端中硬编码每种服务。

### 4.2 注册模型

```ts
interface ToolProviderRegistration {
  id: string;
  name: string;
  transport: 'stdio' | 'http';
  trustLevel: 'local' | 'managed' | 'external';
  tools: ToolDescriptor[];
  enabledWorkspaces: string[];
}
```

### 4.3 权限和凭据

- 凭据存储使用系统安全存储，不进入模型上下文和普通日志。
- 连接器声明读写权限，客户端按调用再次审批。
- 外部写操作不能因为工具已连接而默认授权。
- 工具描述、输入输出 Schema 和错误语义需要版本化。

## 5. 并行 Agent

### 5.1 适用条件

仅在任务可拆分且共享状态受控时使用，例如：

- 一个 Agent 调查后端调用链，另一个调查前端表现。
- 一个 Agent 实现，另一个只读审查。
- 多个独立测试失败分别诊断。

不适合：

- 多个 Agent 同时修改同一文件。
- 需要严格顺序决策的短任务。
- 基础模型无法稳定遵循工具协议时。

### 5.2 隔离模型

- 子 Agent 获得最小工作上下文。
- 默认只读；需要写入时分配不重叠文件范围或独立 worktree。
- 主 Agent 负责合并结论、解决冲突和最终验证。
- 子 Agent 不能扩大权限。
- 并发数、Token、时间和工具调用数有明确上限。

## 6. 专项代码审查

### 6.1 审查模式

- 对未提交差异审查。
- 对指定 commit 审查。
- 对基线分支差异审查。
- 自定义规则审查。

### 6.2 输出要求

每个发现包含：

- 严重度。
- 文件和紧凑行号范围。
- 可触发的问题场景。
- 为什么是缺陷，而非个人风格偏好。
- 最小修复建议。

审查默认只读。实施修复是单独授权的任务阶段。

### 6.3 双阶段验证

复杂修改推荐使用：

1. 实现 Agent 完成修改和测试。
2. 独立审查上下文检查最终 diff。
3. 实现 Agent 根据有效发现修复。
4. 重新运行验证并结束。

## 7. Worktree 和隔离环境

对于长时间或高风险任务，可选创建 Git worktree：

- 不污染用户当前工作目录。
- 支持并行独立任务。
- 任务完成后提供差异、提交或手工合并选择。

创建和删除 worktree 必须显示准确路径并受审批保护。不得自动删除包含未提交修改的 worktree。

## 8. Artifact 系统

长任务会产生超出聊天消息形态的结果：

- 日志文件。
- 测试报告。
- 截图。
- 差异文件。
- 生成的文档和构建产物。

Artifact 需要：

- 唯一 ID、任务 ID、类型、路径、大小和哈希。
- 来源工具和生成时间。
- 生命周期和清理策略。
- 是否包含敏感数据的标记。
- UI 中的打开、复制和导出入口。

## 9. 工具搜索和动态暴露

工具较多后，不应把所有完整描述放进每次请求。建议：

- 初始只暴露核心工具和工具分类。
- 根据任务发现候选工具。
- 只把本轮可能使用的工具 Schema 加入上下文。
- 权限判断始终在客户端执行，不能交给工具搜索结果。

## 10. P2 验收摘要

1. 前端任务可以启动本地页面并留下真实截图和控制台证据。
2. 公网资料结论带来源，且页面提示注入不能触发工具执行。
3. MCP 凭据不会进入模型消息、SQLite 明文或普通日志。
4. 两个只读子 Agent 可并行调查并由主 Agent 合并结果。
5. 同一文件写冲突被调度层阻止。
6. 审查模式不修改工作树，发现包含可定位证据。
7. Worktree 清理不会删除用户未提交修改。

详细条目见 [验收矩阵](05-acceptance-matrix.md)。
